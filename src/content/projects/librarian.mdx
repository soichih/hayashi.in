Every information source in a modern organization is, individually, searchable. Confluence
has a search API; wikis, ticket trackers, and code hosts expose MCP servers; databases are
reachable with a line of code. What nothing provides is the layer *above*: something that
tells an agent — or a new teammate — which of the twenty searchable places exist, what each
one actually contains, and which to try first. That meta-index lives in people's heads, and
it walks out the door when they do.

**Librarian** (working name) is my attempt to build that layer: an MCP server that behaves
like the organization's reference librarian. It knows where things live, teaches you how to
look, remembers what worked — and heals itself when its knowledge goes stale.

## A reference librarian, not a search engine

> Librarian tells you *where to look* and *how to look*, and remembers what actually
> worked. It never does the looking itself.

That last clause is the load-bearing decision: Librarian holds no credentials, runs no
searches, ingests no content. Asked for guidance it returns ranked candidate sources with a
reason for each; per-source affordances ("semantic search via MCP," "keyword-only JQL,"
"ask Dana"); example queries with expected shapes; gotchas; and combination playbooks ("for
outage questions, search the runbooks *and* the postmortems, join on service name"). The
agent then does the actual work and reports back — where the interesting part begins.

## The feedback loop

Most retrieval systems learn from clicks. Librarian records the **task-level outcome**:

1. `how_to_search(question)` → advice, and a session starts.
2. The agent does the work — searches, queries, reads.
3. `report_outcome(session, found?, sources_tried, what_worked, what_failed)` → the truth
   about whether the mentoring helped.
4. Failed sessions return to `follow_up` for new ideas: untried sources, reformulated
   queries, different modalities.

Two memories sit underneath: an **episodic log** (append-only, raw, never shown to anyone)
and the curated **meta-index** of source cards, updated *only* by a curator step that
distills episodes into incremental edits. Never monolithic rewrites — recent
self-improving-context research ([ACE](https://arxiv.org/abs/2510.04618)) shows that path
collapses accumulated knowledge.

## Source cards that test themselves

A text space's card describes what it holds, its depth and freshness, its search
affordances, and which other sources it pairs with. A database's card is a different
animal: a **query cookbook** — distilled schema, verified example queries with expected
outputs, cost and safety notes (analytics replica, not prod; those columns are PII).

The elegant part: the verified example queries in every card **double as canary probes**.
A scheduled run of each example catches schema drift, permission changes, and sources that
died quietly. Cards whose probes keep failing get flagged, demoted, or regenerated —
descriptions are *claims*, and probes test them. Cheap watchers (GitHub org events,
"recently updated" queries) and a human tip line keep the index current without ingesting
anything — new projects start as conversations, not API events.

## Inside and outside the building

The catalog is not bounded by the company. For questions about the world, Librarian routes
outward, and external sources get the same cards with a trust tier (EDGAR/FRED above vendor
data above general web) and an egress note. Two routing shapes show up constantly: is this
a question about *us* or about *the world*? And the hybrid — "how should we recognize
revenue on multi-year contracts?" — follows a **concept + instantiation** playbook:
external source to learn the concept, internal source to find how *we* implemented it.
Outside teaches; inside carries the instance.

Because external scope makes the question space unbounded, the index must grow by
**anticipation**, not inventory. Librarian keeps a coverage matrix — question classes vs.
best internal source vs. best external source vs. *gap* — seeded from what the organization
*is*, then refined by the strongest evidence available: clusters of real searches that
failed. Internal changes feed it too; the company starts selling in the EU, so the watchers
go card the sources that answer the questions that will create. (No upfront taxonomy,
either: [Viva Topics](https://learn.microsoft.com/en-us/microsoft-365/topics/topics-changes-faq?view=o365-worldwide)
never escaped its "bootstrap conundrum" — taxonomies are a human problem.)

And when episodes repeatedly end with "nothing I know covers this," Librarian says so out
loud: *three recent queries failed here; this probably needs a document.* A router that
maps the library's missing books is worth more than one that only points.

## What exists, and what doesn't

The problem is measurable: in a recent benchmark of multi-source information seeking
([InfoMosaic-Bench](https://arxiv.org/abs/2510.02271)), **22% of frontier-model failures
came from selecting the wrong source or tool** — not from reasoning. Routing is the
bottleneck.

The ingredients are all published, separately. Federated-search *resource selection* is
classic IR ([ReSLLM](https://dl.acm.org/doi/10.1145/3701716.3715595) showed LLMs route well
from descriptions alone). Data catalogs like [OpenMetadata](https://open-metadata.org/) and
[DataHub](https://datahubproject.io/) are pivoting agent-facing by ingesting and owning
metadata — the heavy, platform-shaped direction this project avoids. MCP registries route
agents to public tools. A 2026 wave of "librarian" agents
([EMBL's](https://arxiv.org/abs/2607.28229)) knows where knowledge lives — but does the
searching for you. Proactive-agent research ([ProAct](https://arxiv.org/abs/2605.25971))
anticipates needs — for one dialogue, not an org's catalog. Experiential learners like
[ExpeL](https://arxiv.org/abs/2308.10144) distill what worked — inside one agent's memory.

What I can't find, in products or papers, is the synthesis: *thin, tool-poor routing advice
over sources it doesn't control, spanning the company boundary, kept honest by probes,
taught by task-level outcomes, and grown toward the questions the org will ask next.* The
pieces are all claimed; the shape isn't. (Survey current as of September 2026 — I'd love to
be pointed at prior art.)

## Status

Design is done; the build is starting. V1 is deliberately small: a FastMCP server with the
three tools, source cards as markdown in a git repo plus a SQLite episode log, a handful of
seeded cards, one watcher, and the probe loop. No ingestion. No connectors. No credentials
to anything but its own notes.

If it works, the payoff isn't a better search engine. It's an org whose knowledge of *its
own knowledge* stops living in the heads of the people who are about to leave.
